# Aangan call agent: components map (v2)

**Replaces §1 of PLAN.md.** It's built from the real Vaani docs (`docs.vaanivoice.ai`, API at `api.vaanivoice.ai`) and the studio number **+91 84610 08800**, and it's organised around the six traits you shared: hierarchy, state and data flow, responsive rules, tokens, accessibility and events, and ownership.

> **How to read it.** This system has three surfaces people actually touch:
>
> - the **voice call** (Vaani)
> - the **Telegram handoff card**
> - the **dashboard**
>
> Behind them sit a few **backend services**. The UI traits apply in full to the dashboard. For voice and Telegram, the same discipline means building blocks you write once, explicit states, and named owners. Responsive rules and tokens don't apply to a voice call, and I say so rather than invent them.

## 1. Telephony: +91 84610 08800 is a mobile number

A 10-digit number starting with 8 is a **mobile (SIM) number**, not a landline or a cloud number. That decides what's possible:

- **A SIM forwards calls but logs nothing.** GSM forwarding can do busy (`**67*`), no-answer (`**61*…**20#`), unreachable (`**62*`) or forward-all (`**21*`). **It can't route by time of day**, and **it has no API**. So calls the front desk answers, or misses before forwarding, never reach our logs.
- **Vaani has no business-hours schedule.** It accepts calls through Vaani-provisioned numbers (the docs show an Indian `+91 80…` number) or a bring-your-own SIP trunk.

| Option | How | Meets the goals? |
|---|---|---|
| **A. SIM only** | Busy, no-answer (20s) and unreachable on the studio SIM all forward to a Vaani-provisioned Indian number | ❌ After-hours calls ring about 20s before forwarding (not 3 rings). ❌ Front-desk-answered calls aren't logged. ❌ If Vaani fails, there's no record. It fails "every call gets a log row" and "answered %". |
| **B. SIM → cloud number → Vaani** *(recommended)* | Studio SIM: **forward-all** to an Exotel number. The Exotel flow handles time of day. **10am–7pm:** ring the two front-desk phones for 20s, and if nobody answers or they're busy, connect to Vaani. **After hours:** connect to Vaani at once. **If Vaani fails:** voicemail. Exotel's status callback posts every leg to us. | ✅ Every call is logged, including the ones front desk answers. ✅ Real answered % and time to answer. ✅ After hours: about 1 ring. ✅ The fallback is logged. |

Option B also needs: Exotel → Vaani either over **SIP trunk** (Vaani bring-your-own-SIP: host, user, password, port) or as a PSTN connect to Vaani's Indian number. **Test that the original caller ID survives the forward**, because repeat-caller matching depends on it.

## 4. States and data flow

### 4.1 Lifecycle states

**Call (`calls.state`):**

```text
ringing → answered_front_desk ─────────────→ logged_by_front_desk
        → overflow → vaani_live → ended → postprocessed → verdicted
        → after_hours ─┘                  ↘ postprocess_timeout (10 min) → pulled via GET /api/call_details
        → vaani_failed → voicemail → alerted
```

**Enquiry (`enquiries.status`):**

```text
new → qualified → handoff_sent → claimed → consult_requested → consult_confirmed → signed | lost
    → declined(criteria[])        → passed_by_all → escalated_L1 → escalated_L2 → sla_breached
    → nurture(follow_up_at) → (due) → front_desk_queue
    → hold_designer_confirm → Nikhil decides → qualified | declined
    → complaint → paged → acknowledged → resolved
    → merged_into(<enquiry>)            (T17: same number within 30 min)
```

**Handoff card (`TG-ORG-Handoff`):**

| State | What the card shows |
|---|---|
| sent | Full card with Claim and Pass |
| claimed | Buttons removed; "✅ Claimed by Riya · 11:20pm" |
| passed (n) | "Passed by: A, B"; buttons stay |
| escalated L1 / L2 | Line appended: "⏱ 15 min, front desk lead alerted" / "⏱ 30 min, Nikhil alerted" |
| breached | "🔴 Past 60 min" |
| superseded | "🔁 Merged into newer call"; buttons removed |
| error (send failed) | Not visible in Telegram. The retry queue and an `AttentionQueue` item show it. |

Every data organism handles all five states. Each is a named variant in Storybook.

| Component | Loading | Empty | Error | Active / special |

### 4.3 Data flow

- **Server-first.** Pages are React Server Components that read Supabase **views** (`v_kpis`, `v_calls_by_hour`, `v_funnel`, `v_attention`, `v_costs_monthly`) with the user's session. Organisms get plain typed props and never fetch. Only `AttentionQueue` (realtime), `OutcomeEditor`, `FilterBar` and the editors are client components.
- **Filters live in the URL** (`?from=…&to=…&channel=phone`), so a view can be shared and works with the back button. `FilterBar` → `router.replace` → the server re-renders.
- **Writes** go through server actions (`markOutcome`, `confirmConsult`, `updateSetting`, `addInvoice`) that check the role, then `revalidateTag`.
- **Realtime:** `AttentionQueue` subscribes to `handoffs`, `escalations` and `verdicts` changes through Supabase Realtime, falling back to a 30s poll.
- **PII boundary:** views used by charts never join `people`. Only `D-PAGE-Lead` reads `people`, and only after a claim or for founder and front-desk roles.

## 5. Responsive and adaptive rules

Built mobile-first; Nikhil and the designers will mostly open it from a Telegram link on a phone.

| Breakpoint | Width | Shell | Overview layout | Leads | Lead detail |
|---|---|---|---|---|---|
| `sm` | < 640px | Bottom tab bar (Overview, Leads, Attention, More), top bar with title | **Attention queue first**, then KPI tiles in a 2-column grid, then charts stacked at full width | `D-M-LeadCard` list; filters in a bottom sheet | One column: note → criteria → actions (sticky bottom bar) → transcript (collapsed) |
| `md` | 640–1023px | Collapsible icon rail | KPI 3-up; attention and calls-by-hour side by side; other charts 2-up | Table with priority columns (name/locality, status, SLA, designer); the rest goes in a row expander | Two columns: note and criteria on the left, transcript on the right |
| `lg` | ≥ 1024px | Fixed 240px sidebar | KPI 5-up; 12-column grid | Full table, sticky header | Three areas: summary, transcript, outcome editor |

Other rules:

- **Content:** max line length 72ch for transcript text. Numbers use tabular figures.
- **Charts:** at `sm`, `CallsByHour` thins its axis labels to every 3 hours and shows the summary sentence above the chart ("33% after hours").
- **Overflow:** no horizontal page scroll at 320px. Tables become cards, never side-scroll.
- **Zoom:** works at 200% zoom and reflows at 400% (WCAG 1.4.10).
